# English and Brazilian Portuguese localization

Status: architecture agreed in conversation; written spec awaiting review.

## Outcome and decisions

munigan.app supports `en-US` and `pt-BR`. Translate the interface and explanatory
copy. Keep WoW item, gem, spell, talent, class/spec, and tool names in English.
Keep the munigan.app identity, exporter commands, links, IDs, and export formats.

The user chose localized homepage URLs with preference-based tools and reports.
The user also approved browser detection, remembered manual selection, shared
reports in the viewer's language, next-intl, feature dictionaries, and preserving
in-progress work when switching languages.

This document specifies the implementation, not an implementation itself.

## Routes and language resolution

| URL | Behavior |
| --- | --- |
| `/en-us` | English homepage, regardless of browser or cookie |
| `/pt-br` | Brazilian Portuguese homepage, regardless of browser or cookie |
| `/` | Temporary redirect to the preferred homepage |
| `/top-gear` | Same URL in both languages |
| `/reports/{token}` | Same URL and report identity in both languages |
| `/api/*` | Existing API contracts and paths; no locale routing |

For the root redirect and initial workbench render, resolve a valid preference
cookie first, then match `Accept-Language` quality values, then fall back to
`en-US`. Portuguese variants fall back to `pt-BR`; English variants to `en-US`.
Ignore invalid cookie values. Normalize URL slugs separately from BCP 47 locale
identifiers. Unsupported homepage locales return not found rather than rendering
an arbitrary dictionary. Do not generate locale-prefixed tool/report routes.

The root redirect must not be permanently cached across users. Existing report
links, query parameters, and legacy-domain redirects remain compatible. Internal
Overview/brand links target the active language's explicit homepage URL.

An explicit homepage URL controls that page without redirecting to a cookie's
language. Choosing a language manually persists it. Navigating from a localized
homepage into a tool persists the current homepage language before navigation,
so the tool continues in that language.

## Translation architecture

Use next-intl with local, versioned message dictionaries. No translation service,
CMS, runtime machine translation, or separate deployment per language is needed.

Responsibilities:

- `src/i18n/config.ts`: locale allowlist, URL mapping, fallback, and cookie policy.
- `src/i18n/resolve-locale.ts`: deterministic preference/header negotiation.
- `src/i18n/request.ts`: next-intl request configuration and server messages.
- `src/i18n/messages.ts`: explicit lazy loaders for supported message bundles.
- `src/i18n/LocaleProvider.tsx`: active client locale, dictionary loading,
  preference persistence, and switching status.
- `src/i18n/format.ts`: explicit-locale formatting usable outside React.
- `src/i18n/diagnostics.ts`: typed diagnostic presentation and legacy fallback.
- `messages/{en-US,pt-BR}/*.json`: matching feature namespaces.
- `src/features/shell/LanguageSelector.tsx`: shared Base UI control using the
  existing Select design and focus/spacing conventions.

Namespaces cover common controls/accessibility, shell, homepage, import,
inventory/custom items, settings, reports, and diagnostics. Use semantic stable
keys and ICU messages for plurals and interpolation. Do not concatenate sentence
fragments around counts or insert untranslated sentences as parameters.

Keep one set of feature components. Domain models and stored simulation requests
contain values and identifiers, never locale-specific display strings as keys.
Generated simulator code and catalog data remain untouched.

Use separate root layout boundaries for localized marketing pages and the
workbench, reusing a small shared document/shell composition. The marketing root
lives under `(marketing)/[locale]` and resolves its allowlisted route locale,
allowing both homepages to be prerendered without cookie-dependent content.
The `(workbench)` root resolves the visitor preference on the server. The `/`
entry redirects before rendering application content. There is no duplicated
homepage implementation or duplicated tool implementation.

Crossing marketing/workbench root boundaries may load a new document; language
changes inside a tool must not. Keep server-rendered homepage prose on the
server. The workbench shell's visible translated copy is reactive client content
under the locale provider so the whole interface switches together.

Ship the active language messages required by the rendered area. Load the other
language only when requested. The provider must be able to supply namespaces for
subsequent tool/report navigation without a missing-message frame. Measure the
resulting bundle; do not ship translated item catalogs.

## Selector and preserving work

Show a compact language selector in the shared sidebar and mobile navigation,
using `English` and `Português (Brasil)` rather than flags. Translate its
accessible label. Use the current dark surfaces and subtle focus treatment.

On a homepage, switching persists the choice and navigates to the corresponding
homepage. Inside tools/reports, it loads the new messages, persists the choice,
and replaces the provider locale/messages in place. Do not reload, key the tool
tree by locale, or navigate to a second tool URL. Update document language and
the translated client-visible page title. Keep scroll position unchanged.

Persist a non-sensitive `munigan.locale` cookie with Path=/, SameSite=Lax,
one-year lifetime, and Secure on HTTPS. It is readable by the client so the
provider can persist a choice without a server navigation. If persistence is
blocked, the choice still works for the current page session.

Keep the current language visible while another bundle loads. Commit language
and messages atomically; prevent stale requests from winning rapid switches.
If loading fails, keep the current language and show a translated retryable
notice. Initial server and client locale/messages must agree to avoid a language
flash or hydration mismatch.

Preserve raw character and bag text, review step, draft selection, custom item
picker selections/filters, settings, open dialogs, pending submission identity,
report selection/page, and running job polling. Language changes must neither
submit nor cancel a job and must not modify the existing draft storage key.

## Content, formatting, and errors

Translate buttons, navigation descriptions, headings, explanatory copy, form
labels, placeholders, empty/loading states, alerts, toasts, accessibility text,
validation, cap explanations, and generated stat descriptions. English WoW names
are interpolated as data. Keep conventional abbreviations such as DPS and iLvl;
write natural Brazilian Portuguese instead of word-for-word translations.

Stat and socket effects are structured numeric values plus translated labels;
avoid attempting to translate arbitrary catalog descriptions using replacement
rules. Existing English item names and Wowhead tooltips remain English by design.
Locale selection does not expand support for non-English exporter glyph names.

Format displayed quantities, DPS, percentages, and dates with the explicit
active locale. Keep existing precision rules. Percentage helpers must distinguish
fractions from already-scaled percentages to avoid a 100x error. Locale changes
must not round stored numbers or change simulator serialization. Numeric form
controls continue producing canonical numbers and need browser checks in both
locales; JSON/export fields are never reformatted. Absolute dates use a documented
consistent timezone (UTC) to avoid server/client differences.

New user-facing domain/API errors use stable codes and safe parameters, rendered
through messages at the UI boundary. Preserve existing English fallback fields
for compatibility with stored reports and older clients. Extend diagnostic
parameters additively; avoid changing report identity or simulation hashes.
Known legacy error strings can map to codes. Unknown historical errors cannot be
reliably translated: show a localized summary and retain safe original details.
Do not translate raw engine output or expose additional internal error details.

## SEO and sharing

Both homepage URLs render substantive translated HTML without JavaScript. Each
has its own canonical URL, localized title/description, correct `html lang`,
reciprocal `en-US`/`pt-BR` alternates, and `x-default` pointing at `/`. Structured
data includes localized description and language. The sitemap lists both
homepages and language alternatives, excluding tools/reports.

Keep reports crawlable enough for robots directives to be seen, but preserve
`noindex, nofollow, noarchive` and `no-referrer`. Keep Top Gear's existing noindex
policy. API/assets/metadata files must not enter language redirects. Do not cache
cookie-localized HTML as a shared language-neutral response.

Provide localized homepage OG/Twitter title, description, locale fields, image
alt text, and two static image variants using the approved current composition.
Keep the English artwork and adapt only interface/marketing wording for pt-BR;
brand, tool names, and visual styling remain consistent. Keep the favicon shared.
Never include character data or report tokens in homepage metadata.

Share continues to copy `/reports/{token}`. The same saved report renders in
either language without resimulation, duplicated reports, or creator-language
metadata controlling the recipient's interface.

## Verification and rollout

1. Unit checks: locale priority/quality matching, invalid preferences, fallback,
   URL mapping, ICU pluralization, message-key parity and interpolation shapes,
   explicit numeric/percentage formatting, known and unknown error fallback.
2. Browser checks: both homepages with JavaScript disabled; independent canonical,
   alternate, sitemap, OG and lang values; root redirect with different headers
   and cookies; report/API/asset URL compatibility and noindex headers.
3. State checks: switch in both directions while typing an unsaved export, during
   review, after choosing gear, inside a custom picker/settings dialog, and while
   viewing a non-first report page. State and scroll persist; no extra job POST
   occurs. Reload applies the remembered choice.
4. Regression checks: same export/request gives identical IDs, gems, selections,
   simulation input hash, DPS ordering, and cap calculations in both languages.
5. Visual/accessibility checks: 390px and desktop layouts, longer Portuguese
   labels, dropdowns/dialogs/table rows, keyboard interaction, accessible names,
   loading and failure states, and no hydration warnings.
6. Run appropriate existing tests, typecheck/lint and a production build. Compare
   homepage rendering and translation bundle size to the current app. Deploy
   after implementation validation and verify both homepage languages plus an
   existing shared report on munigan.app.

Implement in foundation, shared shell/homepage, Top Gear/import/settings, and
report/error passes, with complete supported-language coverage before production
rollout. No paid localization infrastructure or simulator redesign is included.
