# English and Brazilian Portuguese Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Translate munigan.app into Brazilian Portuguese and US English with localized homepages and stable tool/report URLs, preserving user work during language changes.

**Architecture:** Use next-intl and feature message bundles. Prerender localized marketing routes, resolve workbench language on the server, and switch workbench messages in a stable client provider. Keep locale outside stored simulation requests and local drafts.

**Tech Stack:** Next.js 16.3.4 App Router, React 19.2, TypeScript, next-intl, Base UI 1.8, Tailwind 4.3, Vitest, Playwright, Vercel, existing Trigger worker.

**Spec:** `docs/superpowers/specs/2026-09-09-i18n-design.md`

## Global Constraints

- munigan.app supports `en-US` and `pt-BR`.
- Translate the interface and explanatory copy. Keep WoW item, gem, spell, talent, class/spec, and tool names in English.
- Keep the munigan.app identity, exporter commands, links, IDs, and export formats.
- Do not generate locale-prefixed tool/report routes.
- Keep the current language visible while another bundle loads. Commit language and messages atomically; prevent stale requests from winning rapid switches.
- Share continues to copy `/reports/{token}`.
- No paid localization infrastructure or simulator redesign is included.
- Read the relevant bundled Next.js guides before changing routing/layouts/metadata. This repository uses APIs newer than common Next.js examples.
- The working tree contains earlier approved work. Inspect `git status` before execution; preserve it. Commit only explicitly reviewed paths or hunks. Do not sweep the whole tree into task commits.
- Execute inline unless the user selects delegation. A written recommendation is not permission to spawn agents.

in the shared document module so every rendered root includes them.

Shared interfaces used below:

```ts
type AppLocale = 'en-US' | 'pt-BR';
type MessageArea = 'home' | 'workbench';
type MessageValues = Record<string, string | number>;
type DisplayError = {
  code: string;
  params?: MessageValues;
  message?: string; // safe legacy English fallback
};
type Translation = (key: string, values?: MessageValues) => string;
// config.ts
function isLocale(value: unknown): value is AppLocale;
function homepagePath(locale: AppLocale): '/en-us' | '/pt-br';
function localeFromSlug(slug: string): AppLocale | null;
// resolve-locale.ts
function resolveLocale(cookie: string | undefined, acceptLanguage: string | null): AppLocale;
// messages.ts: Messages is the namespace shape of the English dictionaries
function loadMessages(locale: AppLocale, area: MessageArea): Promise<Messages>;
// LocaleProvider.tsx
function useAppLocale(): {
  locale: AppLocale;
  switching: boolean;
  switchLocale(next: AppLocale): Promise<boolean>;
  persistLocale(): void;
};
// format.ts
function formatNumber(value: number, locale: AppLocale, digits?: number): string;
function formatPercentagePoints(value: number, locale: AppLocale, digits?: number): string;
// diagnostics.ts
function errorDescriptor(error: unknown): DisplayError;
function errorText(error: DisplayError, translate: Translation): string;
```

`loadMessages` returns common/shell plus home messages for home, and all common,
shell, import, inventory, settings, reports, diagnostics messages for workbench.
This keeps client navigation between tools and reports covered without importing
both locales or any translated catalog. Use promise caching per locale/area.
